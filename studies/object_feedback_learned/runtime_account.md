# Runtime measurement and corrected interpretation

The predefined CoTracker3 online probe produced causal, finite outputs on this Apple M2 / 8 GiB Mac. The two-camera steady-update p95 was 2.167 seconds across six full updates. Loading took 0.580 seconds; the first inference took 6.776 seconds, after 0.75 simulated seconds of bootstrap acquisition. The observed maximum driver allocation was 3.670 GB, not a sampled process peak. No geometric accuracy or manipulation success was measured. New Astra requests: zero.

The original 0.4-second criterion was chosen by Sol from an eight-frame update at 20 Hz. It tests keeping pace with real-time acquisition, not a user requirement or a necessary condition for the FYP. The probe failed that particular gate. The stronger statement that this excludes a useful feedback executor was premature: physics can pause during measurement, and a slower feedback rate may improve verified success or reduce expensive model calls despite adding local computation. Preserve the original criterion and failed result, but withdraw its use as an automatic exclusion from further measurement testing.

The next accuracy audit is separately recorded before implementation in [accuracy_decision.md](accuracy_decision.md). It must test only outputs available causally at their actual update endpoints, report bootstrap and intervening measurement age/unknown status, and retain every original query. A passing measurement is a prerequisite for a working bounded-feedback prototype and a new two-start robot comparison. Runtime contributes to actual wall time and cost in that comparison; it is not an unrequested real-time veto.

This is not a failure of H1. H1 has not yet had a robot-policy comparison. The original guard experiment supplies no observed full-task benefit for H3 on two starts, while its wider effect remains unresolved. H2 and H4 are still open. The failed local-flow accuracy screen rejects one estimator configuration, not the general feedback hypothesis.
