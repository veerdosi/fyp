# Sensor audit: LIBERO and native robosuite

The fresh Mac environment rendered the standard task and recorded a 40-step fixed sequence. Its action replay reproduced every flattened MuJoCo state with maximum absolute error 0.0. Evidence: `runs/smoke_001/replay_verification.json`. This is simulator verification, not task success.

## Policy and executor boundary

The policy receives RGB and metric optical-axis depth from `agentview` and `robot0_eye_in_hand` at 256 by 256 pixels, end-effector position and quaternion, seven joint velocities, two finger positions and velocities, and raw wrist force and torque. The whitelist also permits joint positions when the environment emits them; the current ToolHang snapshots do not contain that key. The saved public `observation.json` is authoritative for each run. The force and torque sensors are present in the Panda XML; the wrapper reads robosuite's `ee_force` and `ee_torque` properties and adds them explicitly. These measure local wrist loads including dynamics. They do not certify object acquisition.

Camera images are flipped vertically into the conventional top-left origin. Metric depth conversion and camera calibration use robosuite's camera utilities. Pixel queries unproject depth through camera intrinsics and calibrated camera-to-world transforms. They do not identify objects. Camera mounting and robot kinematics are ideal in this simulation. The moving wrist camera transform comes from simulated robot kinematics, not an estimated object pose. Native camera observables sample inside a control step, while the original public calibration is read at handoff. These timestamps can differ during motion. The object-point development audit captures private image-time references and measures this timing discrepancy separately from correspondence error; neither reference nor private synchronized calibration enters the estimator. No sensor noise was deliberately added, and v1 inputs remain unchanged.

The completed development audit found zero measured camera age in these reconstructed streams and matching image-time/current-step point errors. Initial public unprojection matched image-time geometry to floating-point precision. Calibration timing did not explain this prototype's failure. Matching the original native reset also reproduced all queried RGB/depth/calibration exactly; force-restoring state had changed observable sampling phase in the earlier audit attempts. See [the measurement account](../studies/object_feedback_feasibility/account.md).

The direct executor uses measured end-effector pose to realize a fixed model-selected absolute pose through native OSC_POSE delta actions. It uses no vision, object estimate, reward, contact truth, or task stage. It executes the full declared duration. It can validate commands and enforce common target bounds, 0.015m translation and 0.15rad orientation updates at 20Hz. A target bound is not a collision-avoidance planner.

The v1 measured guards retain that conversion and use permitted end-effector poses and finger velocity to test arrival/settling. Linear and angular speeds are derived from consecutive robot poses at the shared control period. Every condition receives the same derived execution report after motion. Guard exits change sequence progression and handoff, not the motion target or task plan. No raw wrist load or object/contact predicate drives a v1 exit. The exact criteria and five replayed execution/duration checks are in [phase_execution.md](phase_execution.md).

## Excluded simulator information

Default LIBERO observations include each mug's world position, quaternion and pose relative to the gripper, plus an `object-state` vector. None is present in the public policy folder. These are written only to step diagnostics. MuJoCo state, task reward, collision contacts, task predicates and success are also excluded from policy inputs and execution decisions. Task success is checked after execution for scoring; it does not end an episode automatically.

Every control step records the pose and finger/load measurements used by the executor, the native action, post-step robot readings, and separate diagnostic object observations. Camera RGB-D is saved at each model handoff; the direct executor does not consume camera frames during motion. A two-view video records every control step. Saved initial state, actions and state trajectory support deterministic action replay.

## Pilot scope

Physics is paused during model calls. These pilots measure bounded robot decisions, not real-time robustness to inference delay. Sensing-only decisions count against the same policy-decision budget as motion decisions. Native agent sessions expose per-request token records and turn timing. `policy_usage.json` distinguishes policy decisions from model inference requests, which also include requests surrounding image and sensor-reading tool calls. It records a standard API-equivalent estimate using documented Astra rates, with actual account charge left unknown. A fixed non-model verification sequence uses zero model calls.

See [policy_boundary.md](policy_boundary.md) for the boundary and tool-log audit. Astra may write and execute logged temporary calculations from public sensor inputs in its own episode calculation directory. It may not modify experiment code or access simulator-only information. This is an instructed and audited boundary, not a filesystem sandbox.

## Native precision-task adapter

The native robosuite adapter uses the existing Panda, OSC_POSE controller, object geometry, placement sampler and benchmark success checks. It exposes the same whitelisted camera and robot readings through the shared episode code. Object pose, frame assembly, tool-hook contact, reward and success remain private diagnostics. No task-specific grasp, alignment, insertion or recovery routine is added.

`smoke_nut_square_001` and `smoke_tool_hang_001` each recorded 60 fixed control steps, including the shared 20-step initial settling period, with zero policy calls. Both action replays reproduced every saved state exactly. These checks verify the adapter and recording path; neither is a task-success demonstration.

The successful `pilot_tool_hang_001` also replayed all 1855 saved states exactly. After that pilot, common logging added setup and per-command wall-time components, so subsequent runs can separate execution, policy time and operator/orchestration gaps. The same change closes an episode when its final budgeted decision is rejected, rather than leaving the server waiting. `verify_rejected_budget_001` exercised that case in the real scene with one operator request, zero policy inference and only 20 settling steps. Its action replay also has zero state error. The run contains a script to reproduce the closure check in a new directory; it is excluded from policy success statistics.

## Robot feedback beyond image tracking

The [robot-feedback screen](../studies/robot_feedback_modalities/account.md) uses only public robot poses, finger readings and wrist loads to derive progress, empty-sized closure and load-change warnings. Two predefined free-motion calibration runs fit an empty-gripper gravity reference from public orientation and finger opening. Private geometry only verifies that the calibration sequence was free of unintended contact; it is excluded from the fit, monitor and policy. Held-out quiet orientations verify this deterministic simulator reference, not physical sensor accuracy. Held-object weight and dynamics remain in compensated loads.

The [v2 interface](../studies/tool_hang_v2/protocol.md) publishes identical compact sensor summaries, calibration coefficients and optional full 20 Hz rows in both conditions. Only an explicitly armed empty-sized closure can interrupt the guarded condition. It requires closed-command finger opening at most 2.9997 mm, finger-speed norm at most 1 mm/s, three consecutive readings and at least ten executed waypoint steps. The timed condition reports the same warning after completing its requested duration. Load and stalled-motion warnings remain advisory because the screen found dynamic confounds and missed an upstream arm collision. Neither a non-empty closure nor a load change certifies acquisition, seating, collision clearance or task completion.

Fixed paired fixtures verify an empty lift is interrupted and a successful regrasp is allowed, with exact state and robot-sensor replay. Shared-publication verification confirms equal sensor products when actions match. Actual Astra episodes are a separate policy-benefit test. [The initial-input erratum](../studies/tool_hang_v2/amendment_002_encrypted_input_erratum.json) records that the first episode's native initial prompt is encrypted and its exact plaintext was not preserved. Its scheduled outcome remains in the account, but the first pair cannot isolate the stopping semantics. Subsequent inputs are preserved before dispatch; the second start uses matched common instructions.
